For those unfamiliar the game has a feature where items of greater quality have a random chance of being produced, and if you are dissatisfied with the quality you can 'recycle' the item at the risk of destroying it, but with the chance of getting a better result.

The game's official wiki has some useful info on deciding how to decide on a ratio of modules to use to optimize higher quality results. "Should I maximize quality chance, or should I increase productivity so that I produce more items and by that means get more high-quality items?" The math on this is pretty straightforward, given productivity P and quality improvement chance Q you can expect to get P*Q higher quality items. I decided to attempt a problem that was both far more difficult to calculate and, crucially, had almost no practical use: what are the odds of a given item going through the recycling process will reach the highest quality, legendary?

It was intuitively obvious that the solution would be recursive, although that's not quite the way I solved it. What ended up helping was visualizing it with something of a sloppy state diagram. There we can see that there is a chance of entering a fail state, F, and a chance of continuing processing 1-F. At that point there is a chance, Q (split in the diagram into .9Q and .1Q, for reasons I won't bore you with), of getting a higher quality item. This leaves a chance, 1-Q, of having the item remain at the current quality. Thus proceeding to the second run through the recycler, the second recursion, is (1-F)*(1-Q). From there the same odds play out.

Adding those happy states up gives us the summation you see next to the state diagram. I've skipped some steps in the math here that would require me explaining the game's mechanics, but the upshot is that I now had a singular equation I could use. The next step was to turn the summation into a non-summation function and then assess the limit of that function as its end point approaches infinity. I've been out of university for a while so I don't recall any summation identities that would help me with that so I cheated for this step and let WolframAlpha do it. This left me not entirely confident in my results, so I resolved to do something you're not supposed to do in math and test it out in practice.

I set aside 201,600 of the game's most basic items. Based on the quality modules I had available to me at the time my tool calculated these would turn into 72 items of the highest quality. I left the game on overnight as the recyclers did their thing and the result was 73. Close enough to account for the stochastic nature of the process, so I'm calling it a success!

If you've worked in systems that use inversion of control, especially in something distributed like microservices, you've probably had a set of beans that would be shared across multiple code bases. Because code duplication is bad you made a library to house them. In the stage of the project I'm at currently that's most of what I'm working on. Micronaut has a built in library Gradle plugin that makes this nice and easy, but this library plugin has a little quirk. I can't find any documentation stating this explicitly but it appears that even in testing you can't fire up an embedded server.

A library has no need for a runner so this makes sense. The problem is that my libraries are very controller-heavy as I implement shared behavior across plugins. If I can't fire up the server then I can't have running controllers to make requests against in the unit tests. It's leaving a sizeable hole in my test coverage.

The good news is that this is both a very solvable problem and one that carries very few risks. There are a few options for solving it, probably involving having dedicated test services that exist just for the libraries to test against. The TestEmbdeddedServer seems to be designed for that eventuality. I say low-risk because these endpoints are mostly pass-throughs that are hard to mess up. There's even the question of how much more I'd really get out of these tests because I'm disabling Micronaut-security in the tests. Desk-checking is necessary to properly see the behavior anyway.

I make this post mostly so I'll remember to come back and solve it eventually, but this is going to end up being a low-priority issue. Anyway the dog keeps bringing me a ball so I guess I have to play with her now.

It started innocently enough. Micronaut, as part of the client_credentials OAuth flow, was attempting to make requests of Keycloak at localhost instead of host.docker.internal, the host it knew for Keycloak in the very rudimentary Docker setup I was using at the time. This didn't take long to diagnose. Wherever Keycloak may be it sees itself as being at localhost and that's what's going to show up in the well-known OIDC page. Some Docker networking, the keycloak hostname attribute, and maybe some tinkering with my Hosts file would resolve this, EZPZ.

I was a fool.

Setting up a Docker network with Keycloak hostname attribute using the network alias does allow the client_credentials flow to proceed as desired, but the Keycloak admin console is unusable. This wouldn't necessarily be a deal breaker, but I suspected it would also break the standard flow logins as Micronaut uses the issuer property to know how to redirect to the login page. This might have been easily resolved with the hostname-admin Keycloak attribute, but it seemed to be bugged. I found github discussions, Stack Overflow Posts, and forum discussions matching strange hanging behavior I was seeing. Even more confusing were the posts from Keycloak developers pointing to closed tasks to resolve this problem. I hoped I could resolve this with the hostname-backchannel-dynamic attribute and setting the hostname to where the admin console lives. That allowed the client to get a token, but the token would have an issuer matching the hostname, which would not match the issuer the resource server expected. This made sense as I developed a better understanding of Keycloak where "backend" refers specifically to the admin API and not to authentication flows that do not require direct user interaction such as client_credentials. I resolved to instead use a reverse proxy to force the host by which the host machine sees keycloak to match how my client services see it.

Any readers familiar with reverse proxies are probably shouting at their screens that this obviously won't work. "John", they shout, "You absolute turnip! Reverse proxies control how requestors outside of the proxied network see servers, not how those internal servers see each other!" Well...I didn't know that. In fact I was optimistic about reverse proxies being something I might want to incorporate into the psn ecosystem going forward. So I set up Traefik in my compose.yaml and set myself up with some nice *.localhost domains and fire up the whole ecosystem, which immediately fails. The error as Micronaut prints it in the console is a connection refused at keycloak.localhost/127.0.0.1:80, a bizarre hostname that I was sure must be a product of some strange interaction with Keycloak in Traefik. With the benefit of hindsight I can see that this was simply Micronaut showing me both the hostname I had given it and the IP/port to which it resolved. At the time, however, I was so confused I even brought it to the Traefik forum asking for help before recreating the exact same error in NGINX proxy manager. My deepest apologies to the Traefik developers for impugning your product.

My suspicion now was a bug in Micronaut. I made some brief investigations into the micronaut-security code before deciding to just attempt to recreate the problem in Spring Boot the same way I might check if a charging cable is broken by swapping it out for another charging cable rather than opening it up and looking for a severed wire. This proved somewhat difficult to prove because although the exact same problem happened with Spring Boot I had hyper-fixated on the strange-seeming way Micronaut printed the host in the error message, which Spring Boot didn't do. Once I put that together I realized I had ruled out Micronaut and Traefik as the cause of my problem, I knew it couldn't be Keycloak because I can cURL the well-known OIDC page from inside the Docker containers, and if Docker is the problem I might as well pack all this up and go home. This is where I finally put together that I had misunderstood how proxies work and they were never the solution to this problem. There may have been a way to finagle the ecosystem so that Keycloak had a separate proxy from the clients, but I chose not to pursue this.

It's worth noting that in the week-ish I had spent on this I was always aware that this wasn't a problem I necessarily need to solve. The hosting service I use will naturally put all of these at separate domains so the confusion over host vs Docker is immaterial. It's also not necessary for development. I can just use Docker for keycloak and a database while running the web services directly on the host as I had originally done it in the various spikes. It introduces some risk since the host service I'm using closely mirrors Docker, but nothing serious. For this reason I had time boxed myself until the upcoming weekend.

The craziest twist came on the last day of the time I'd given myself to solve this. I had, at some point, set the hostname-strict attribute to false without it solving the problem I was having. It was only when I accidentally left the hostname-admin and hostname attributes commented out when starting a run that I suddenly found myself with a functioning client_credentials flow and an admin console accessible from the host machine. Was this it? Had I finally solved it!?

No. Of course I hadn't. I still needed the standard flow to work and adding a basic Thymeleaf UI confirmed the worries I mentioned a few paragraphs ago. /oauth/login/keycloak was redirecting to keycloak:8080 and was thus unusable from the host machine. My time box had expired and it was time to fall back on running my services on the host machine.

I want to close this, my longest post thus far, with the unexplored options. When I checked the Micronaut documentation I couldn't find anything that would allow me control the host domain for login redirects, something that should be possible under the standard flow. It should still be possible to find the bean that makes the login redirect and replace it with one that can accept a custom host. I haven't looked deeply into alternate Docker configurations such as a second Docker engine or Docker swarms, but one of these might be able to create the kind of environment I need here. I could get Keycloak running on my web host and and simply maintain a development realm. The fact that I can have as many realms as I want means I wouldn't even have to worry about situations where I need to branch my Keycloak configuration.

When I originally planned on having a dedicated plugin for user management I had been envisioning a traditional database-backed web service. I would have a "create user" endpoint that would save the user's info to a database, probably Postgres. Keycloak was intended only for authentication and authorization, the only interaction I would have with it would be saving the username and adding roles to users to their access token could be up-to-date.

As I work more and more with Keycloak I'm learning I don't need to do most of that. I can store an entire user's profile, including custom fields. I can use a provided login and registration page. I can even define groups of roles so when, say, someone is promoted to moderator we can just add them to the moderator group. No need to keep a role/group mapping table for the user plugin. In fact all user administration could be done within the admin console. I can save myself the effort of making an admin client entirely!

What I don't have, at least out-of-the-box, is the ability to limit behavior within the admin console. If I want someone to be able to promote moderators for a specific plugin I would have to make them also able to add plugins. Obviously I can control this by making mod promotion a user-plugin behavior, but then I have to make a UI around that. Keycloak does have a feature for more fine-grain control, but it is regarded as a "preview" in the most current version (25.0.0 at time of this post) and thus not recommended for production use. I'm leaning toward just using it anyway, not that I have any immediate need for anyone but me to administer a server anyway.

The first time I ever heard of a protocol-based social network was in a discussion about hypothetical anti-trust action taken against Facebook. We could picture Facebook being split into two different platforms, as had been done with AT&T in 1982, but it's hard to imagine it working with a social network. I would want to be on the same baby-Facebook as my friends, who would want to join their friends, and before long we'd be right back at there being only one de-facto Facebook again. We could also imagine a judgement that such a product as Facebook could never be anything but a consumer-hostile monopoly and that it should be nationalized and operated as a public good, similar (from a legal perspective) to how NPR works, but we live in a post-Reagan America so anyone proposing such an idea would be run out of congress as a communist agent. The solution that was proposed to me at the time was to abolish Facebook as a platform and instead reimagine it as a shared form of communication that could be distributed across many small platforms: a protocol. Schools, local governments, companies, and even particularly enterprising individuals could host their own Facebooks, with the shared protocols allowing them to interact as seamlessly as the centralized platform, but with no overarching owner to control it.

Although this idea isn't any more likely to be put into practice under the Sherman Antitrust Act than the previous ideas, it has the benefit of being actionable. It has, in fact, been acted on. Mastodon and Bluesky both operate on a similar principle, although their model is more similar to Twitter than to Facebook. This gives us a look at how this concept can work in practice. They certainly haven't developed the same market penetration that their centralized alternative has, but we at least can see this as achievable from a technical perspective.

So why would I throw my own hat in this ring? Well the first time I tried it it was just an excuse to refresh myself on Spring Boot, a technology I hadn't touched in the better part of a decade, when I was laid off from the company that made Micronaut. Now that my day job is almost exclusively Spring Boot I wanted to revisit the idea in Micronaut and keep that skill sharp as well.

One thing I'm doing a bit different than the existing distributed social networks, at least to the best of my knowledge, is maintaining a degree of extensibility to individual nodes. My focus in this very early stage is features that would be universal such as user management and administration with virtually every actual user feature being an optional plugin that could be added on. Do you want your node on this social network to feature blogging? That's a plugin. Did you want to upload images to display in your blogs? Better provide a file hosting plugin too. Of course I have to call myself out a bit on this idea as well. Making a tool that can do anything is easy. That's a compiler, and every computer science student makes one in a 300-level class. Making a tool that can do anything and then doing anything useful with it will be the real challenge.

I want to close on speculating about use-cases for a tool like this. There are plenty of complaints about the existing social networks. Algorithmic feeds that leads to addiction. The ease with which misinformation spreads. That time Facebook maybe caused a genocide in Myanmar. Knowing that these distributed networks are unlikely to actually displace the established social networks means focusing on ending the harm they cause isn't productive. It's better to look at the uses people might find outside of those existing social networks. We can imagine, for example, small isolated nodes for people who just want to keep in touch with friends but don't want the baggage of being on the larger social networks. We can look at the ability for niche tools or even video games that can be integrated directly into a social network. A frequent complaint among online sex workers is that they are driven off of social networks (in 2021 OnlyFans threatened to ban them, and I thought until then that was the point of that site), a problem that could possibly be alleviate by having a social network under their own control. One might even imagine labor organizers being able to collect union support without workers having to reveal the intent and risk retaliation.

But these are very pie-in-the-sky ideas and this 0.1 release is a long way from anything like that.
